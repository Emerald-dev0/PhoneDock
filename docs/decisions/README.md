# Architecture decision records

Store accepted architecture decisions here using short, numbered records, for example `0001-short-title.md`. An ADR should capture a real decision that affects multiple components, future compatibility, security, platform support, or migration—not a proposal or an issue that has not been resolved.

Each record should state its status (`Proposed`, `Accepted`, `Superseded`, or `Rejected`), date, context/problem, constraints, options considered, decision, consequences/trade-offs, links to requirements and implementation, and how it will be revisited. Link superseding records rather than rewriting historical rationale.

**No architecture/protocol/platform decision is recorded as accepted in Phase 0.** The protocol, shared-code boundaries, identity/pairing, transport security, platform technology choices and proposed visual direction remain open. The accompanying documentation deliberately labels them as proposals; do not infer approval from the target organization or roadmap.
