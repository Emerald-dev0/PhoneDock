# Platform support and capability matrix

This page separates **source found in the repository**, **intended product scope**, and—on iOS—**public-API feasibility**. A directory, UI, API, or plan is not proof that an end-user capability is implemented or supported. Status/evidence rules are in [FEATURE_STATUS.md](FEATURE_STATUS.md); product requirements are in [PRODUCT_SPEC.md](PRODUCT_SPEC.md); phase dependencies and verification gates are in [ROADMAP.md](ROADMAP.md).

**Research snapshot:** iOS API classifications and hosted Apple tool versions below were reviewed on **2026-10-01**. Recheck current Apple documentation, SDK/policy requirements, and GitHub runner inventory when Phase 4 begins and before a capability/support claim. All iOS PhoneDock features remain **planned/not implemented**.

## iOS public-API feasibility matrix

These four labels describe whether ordinary public APIs appear capable of a **carefully scoped** workflow. They are not PhoneDock implementation statuses, Apple approval, or guarantees for every iOS version/device. A feature remains unimplemented until its protocol, product/security design, code, tests, and platform evidence exist.

- **Documented-API implementable** — documented public APIs exist for the app-owned behavior; product/protocol decisions and testing are still required.
- **Restricted/user-mediated** — an API exists only with scoped permission, system UI, user selection, or lifecycle constraints; do not promise unattended behavior.
- **Requires further investigation** — a possible API/transport exists, but the exact PhoneDock workflow, version, accessory, entitlement, policy, or interoperability is unresolved.
- **Unavailable through ordinary public APIs** — the specified cross-app/system-level behavior is not exposed to an ordinary third-party app; exclude it unless Apple documents an applicable supported route.

|---|---|---|---|

[TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) requires a user-facing local-network explanation; declare relevant `_phonedock._tcp` usage in [`NSBonjourServices`](https://developer.apple.com/documentation/bundleresources/information-property-list/nsbonjourservices) and handle denied/revoked access. | **Authentication and encrypted sessions** | **Documented-API implementable** | Apple provides [`CryptoKit`](https://developer.apple.com/documentation/cryptokit) and [`Keychain Services`](https://developer.apple.com/documentation/security/keychain-services) for cryptographic operations and protected key storage; [`Network.framework`](https://developer.apple.com/documentation/network) provides networking/security protocol APIs. ## Platform restrictions and verification expectations

- **Android:** screen capture requires user consent and lifecycle compliance. Remote interaction, background operation, local-network discovery, and notifications have separate API/permission limits. The manifest and target SDK are not a compatibility test. Capture/encoder support and performance vary by device.
- **iOS:** no PhoneDock capability is implemented. Use the feasibility matrix and current Apple docs before claiming anything. Local-network consent/discovery, protected file selection, clipboard, background execution, capture, MFi accessories, other-app notifications, media controls, and remote input have distinct limits. ScreenCaptureKit iOS 27 is beta at this research snapshot; ReplayKit APIs listed above are deprecated for iOS 27. Never promise Android parity by analogy.
- **Linux:** discovery, multimedia codecs, display session, packaging, sandboxing, and device permissions vary across distributions and desktop sessions. Declare supported distributions and validate them before release.
- **Windows:** app APIs and codecs vary by Windows/SDK/hardware; display-driver functionality separately requires WDK, signing, deployment, recovery, and OS-version work. A `.vcxproj` is not proof of a working app/driver.
- **macOS:** local-network privacy, sandboxing, file access, screen-capture consent, signing/notarization, and distribution differ from iOS/Linux. An iOS Simulator runner is build infrastructure, not a macOS PhoneDock implementation.
- **Web:** browser APIs are constrained by same-origin/security models, permissions, and background lifecycle. A web client cannot be assumed to open arbitrary native TCP connections or implement a native display/driver path.

## Build and test evidence policy

- Existing CI continues to cover repository/documentation checks, Linux desktop dependencies/source/smoke checks, Android Gradle checks, and the Windows C++ app build. The latest verified run is [36652649534](https://github.com/Emerald-dev0/PhoneDock/actions/runs/36652649534). No iOS/macOS job exists because those app projects/schemes are absent; no web job exists because web source is absent; no driver job exists because driver implementation/WDK setup is absent.
- Phase 4 plans a least-privilege macOS runner job **only after** a real iOS project, scheme, and repeatable XCTest/Simulator command exist. The verified 2026-10-01 candidate is `macos-26` / Xcode 26.6 / Swift 6.3 / iOS 26.5 Simulator; re-check the hosted image and stable Apple system-requirements matrix at kickoff. `macos-latest` is not a reproducibility pin. Record the runner image version, `xcodebuild`/Swift versions, SDK, simulator runtime/destination, command, and result bundle/log.
- The iOS Simulator is Apple's Xcode simulator and runs on macOS. Linux Swift can test deliberately portable source only where a compatible Swift toolchain is available; it cannot build an iOS target or run the official Simulator. Do not create a custom emulator.
- Simulator tests can establish compilation, unit/state logic, protocol fixtures, navigation, layout, and practical UI automation for that runtime. They cannot establish physical iPhone Wi-Fi/Bonjour, app/device permission behavior across hardware, radio/USB behavior, sustained background execution, capture quality, battery, thermal performance, or peer interoperability.
- A successful build establishes buildability for that runner/toolchain only. It does not establish discovery, session security, video, input, transfer, or hardware compatibility.
- Update each feature row only with CI or named platform/device evidence as defined in [FEATURE_STATUS.md](FEATURE_STATUS.md) and [TESTING.md](TESTING.md).
- There is no claimed supported release matrix. Add device/OS/distribution/browser versions only when actually tested and maintained.
